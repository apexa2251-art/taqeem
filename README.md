# تعقيم — Taqeem

تطبيق عربي / إنجليزي مبني بـ React وJavaScript وNode.js/Express، للنشر على Render واستخدام Supabase Auth وPostgreSQL وStorage.

## الهوية والواجهة

تستخدم الواجهة اللوقو المصمم لـ STERILOG وصورة توضيحية مولّدة لقسم تعقيم، وليست صورة لمنشأة المستخدم. خط العربي IBM Plex Sans Arabic وخط الإنجليزي Inter، مع ملفات خطوط مضمنة محلياً ضمن البناء، دون اعتماد على طلب الخطوط من Google عند التصفح. تراخيص الخطوط في `public/licenses/`.

## ما نُفّذ

- فرعان مستقلان: **تعقيم بريدة** و**تعقيم عنيزة**.
- لكل موظف حساب شخصي؛ اسم المُدخل يُسجل من ملفه المحمي تلقائياً، واسم المراجع يسجل من حساب المراجع. لا يوجد حقل اسم حر يمكن تغييره في نموذج الدورة.
- مسؤول عام يرى الفرعين، وأدوار حسب الفرع: مُدخل، مراجع مخول، مسؤول فرع، عرض فقط. الموظف الذي يعمل بالفرعين يمكن منحه عضوية في كليهما.
- أربعة أجهزة غير موزعة على الفروع وغير مفعّلة عند البداية. لا يفترض النظام وجود أربعة أجهزة في كل فرع.
- برامج جهاز مستقلة بمعايير قبول يحددها المسؤول من المرجع المعتمد؛ لا توجد حرارة أو مدة افتراضية للاستخدام السريري.
- دورة بثلاث مراحل، عدة أنواع أطقم وكميات ومعرّفات، وعدد عبوات مستقل، قراءات فعلية، وM/C/D، ومرفق تقرير خاص.
- المسودة قابلة لتعديل مُدخلها فقط. الإرسال يقفلها. اعتماد الاستخدام يحتاج مراجعاً آخر مخولاً. الحجز والرفض يتطلبان سبباً وإجراءً.
- التصحيح الموثق يحفظ الإصدار السابق، ويعيد السجل مسودة بإصدار جديد، ويتطلب تقريراً خاصاً بالإصدار الجديد.
- تسجيل الاختبارات الحيوية والشاهد والفحوص، وتنبيهات داخل التطبيق مبنية على السجلات؛ قراءة التنبيه لا تغير حالة الحمولة.
- تقارير قابلة للطباعة A4 أفقي وحفظ PDF من المتصفح، وCSV عربي/إنجليزي محمي من صيغ الجداول.
- سجل تدقيق لا تملكه صلاحية التعديل أو الحذف من حسابات التطبيق، ومرفقات خاصة وروابط قصيرة الصلاحية.

## أسماء الربط

اسم النظام ومشروع Supabase: **تعقيم**. الاسم التقني المقترح لمستودع GitHub وخدمة Render: **taqeem**. اللوقو المعتمد STERILOG محفوظ داخل الواجهة.

ملف `render.yaml` يحدد الخطة `free` صراحةً. قاعدة البيانات يجب أن تكون في مشروع Supabase جديد مستقل على الخطة المجانية، ولا تشارك قاعدة Masar. ملف SQL يرفض العمل إذا وجد جداول تطبيق موجودة مسبقاً في public.

راجع `DEPLOYMENT.md` لخطوات الربط المختصرة.

## التشغيل لأول مرة

### 1. مشروع Supabase

1. أنشئ مشروع Supabase جديداً مخصصاً لهذا النظام.
2. نفذ ملف `supabase/migrations/001_sterilog.sql` مرة واحدة من SQL Editor. الملف لإنشاء قاعدة جديدة، وليس ترقيع قاعدة مستخدمة.
3. في Authentication عطّل التسجيل العام، واضبط Site URL وRedirect URL إلى عنوان التطبيق على Render. فعّل إعدادات كلمة مرور مناسبة. استعادة كلمة المرور بالبريد غير متاحة في واجهة التطبيق؛ تحديث بيانات الدخول يتم بواسطة مسؤول النظام.
4. أنشئ أول مستخدم من لوحة Supabase Authentication باستخدام بريد المسؤول وكلمة مرور يختارها بنفسه. لا توجد كلمة مرور افتراضية في المشروع.
5. انسخ `.env.example` إلى `.env` محلياً واضبط `SUPABASE_URL` و`SUPABASE_PUBLISHABLE_KEY`.
6. لإنشاء ملف المسؤول العام، أضف محلياً فقط `SUPABASE_SECRET_KEY` و`ADMIN_EMAIL` و`ADMIN_NAME` ثم شغّل:

```bash
npm ci
npm run bootstrap
```

هذا الأمر يربط مستخدماً موجوداً مسبقاً بملف مسؤول؛ لا ينشئ بريداً ولا يرسل رسالة. المفتاح السري لا يحتاجه خادم التطبيق على Render ولا يرسل للواجهة.

### 2. إنشاء موظفين

من تبويب «المستخدمون» يستطيع المسؤول العام إنشاء حساب موظف باسمه وبريد الدخول والفرع والدور وكلمة مرور من 12 إلى 128 حرفًا؛ لا ترسل رسالة تأكيد. يستطيع المسؤول تعيين كلمة مرور لموظف، ويستطيع كل موظف تغيير كلمة مروره من التبويب نفسه.

يلزم نشر وظيفة Supabase `manage-staff` من `supabase/functions/manage-staff` مع الإعداد المرفق في `supabase/config.toml`. تستخدم الوظيفة مفاتيح الخادم التي توفرها Supabase داخل بيئة Edge فقط، وتتحقق من JWT عبر `getUser` ثم من ملف الحساب الفعّال وصلاحية المسؤول. لا يضاف مفتاح سري إلى Render أو المتصفح. تسجل عمليات الحسابات في سجل التدقيق دون كلمات المرور. الاستعادة الإدارية من لوحة Supabase مقيدة بحساب مسؤول عام موجود وفعّال وبمفتاح خادم صالح، ولا تنشئ حسابات أو تمنح صلاحيات.

بديل إداري يدوي عند الحاجة: أنشئ مستخدم Auth لكل موظف من لوحة Supabase أولاً، ثم استخدم الأمر المحلي التالي مع متغيرات البيئة المناسبة:

```bash
node --env-file=.env scripts/provision-staff.js
```

المتغيرات: `STAFF_EMAIL`، `STAFF_NAME`، `STAFF_BRANCH` بقيمة `buraydah` أو `unayzah`، و`STAFF_ROLE` بقيمة `operator` أو `reviewer` أو `branch_admin` أو `viewer`. يستخدم نفس مفتاح المسؤول السري المحلي. يحافظ الأمر على ملف المسؤول إذا كان موجوداً ولا يحوّل حساباً إلى مسؤول عام. يمكن للمسؤول العام لاحقاً تعديل عضويات الفرعين من تبويب المستخدمين. تعديل أسماء الملفات أو تعطيل الحسابات حالياً يتم من لوحة المسؤول في Supabase.

### 3. تشغيل محلي

```bash
npm ci
npm test
npm run build
npm start
```

افتح `http://localhost:3000`. بدون إعداد Supabase يعرض النظام بوضوح أن الإعداد مطلوب؛ لا يوجد دخول تجريبي أو حفظ محلي يوهم بحفظ سجلات حقيقية.

للتطوير المباشر: شغّل `npm run dev:server` في طرفية و`npm run dev:client` في أخرى؛ Vite يمرر `/api` إلى المنفذ 3000.

### 4. النشر على Render

ارفع هذا المجلد إلى مستودع Git، ثم استخدم `render.yaml` أو أنشئ Node Web Service:

- Build: `npm ci --include=dev && npm run build`
- Start: `npm start`
- Health check: `/api/health`
- Node: 22 أو أحدث.
- Environment: `NODE_ENV=production`، `SUPABASE_URL`، `SUPABASE_PUBLISHABLE_KEY` فقط. يدعم `process.env.PORT` والاستماع على `0.0.0.0`.
- لا تستخدم قرص Render لحفظ المرفقات؛ تحفظ في Supabase Storage الخاص.

بعد النشر عدّل عناوين إعادة توجيه Auth إلى رابطك النهائي. لا ترفع `.env` إلى Git.

### 5. إعداد الفرعين والأجهزة

1. ادخل بحساب المسؤول العام واختر تعقيم بريدة.
2. افتح «الأجهزة والبرامج»، واربط الأجهزة الموجودة فعلياً في بريدة بهذا الفرع، وأكمل الطراز والرقم التسلسلي ومرجع IFU وفعلها.
3. انتقل لتعقيم عنيزة وكرر للأجهزة الموجودة فيها. لا تنقل جهازاً له تاريخ دورات عبر نموذج التعيين؛ النظام يمنع ذلك لحفظ التتبع.
4. أضف برامج كل جهاز ومعايير القبول من مستند معتمد. القيم في ملفات الاختبارات صناعية للاختبار فقط ولا تُستخدم سريرياً.
5. وفّر حسابين مخولين على الأقل إذا أردت إدخال السجل ثم اعتماده؛ المُدخل لا يعتمد استخدام حمولته بنفسه.

## طريقة العمل

اختر الفرع → دورة جديدة → الجهاز والحمولة → القراءات والفحوص → التقرير والإرسال → المراجعة والاعتماد. الحفظ كمسودة متاح قبل اكتمال التفاصيل، لكن إرسال السجل يتطلب البيانات والأدلة. الأسماء لا تؤخذ من نص يكتبه العميل؛ قاعدة البيانات تستخرجها من هوية الحساب الموثقة.

الاختبارات الحيوية تسجّل كأحداث غير قابلة للتعديل. عند قراءة نتيجة معلقة، سجّل قراءة جديدة لنفس الدورة مع بيانات التشغيلة والشاهد؛ تستخدم أحدث قراءة مرتبطة بالدورة عند فحص شرط BI. لا يتم افتراض زمن حضانة أو معيار لون معين.

## الأمان والاختبارات

`npm test` يشغّل اختبارات منطق العمل وHTTP وSQL مع محرك PostgreSQL محلي PGlite. يتم اختبار ملف migration الحقيقي مع جداول Auth وStorage بديلة للاختبار، بما يشمل فصل الفرعين، منع انتحال الاسم، منع ترقية الحساب لنفسه، عدم تعديل السجل بعد الإرسال، حفظ الإصدارات، حواجز اعتماد الاستخدام، والمرفقات الخاصة. توجد أيضاً اختبارات توقيت السعودية وتحييد صيغ CSV.

هذه الاختبارات لا تدعي اختبار خدمة Supabase أو Render الحقيقية. بعد ربط المشروعين يلزم اختبار دخول بحساب من كل فرع، رفع ملف حقيقي، مراجعة بحساب آخر، والتأكد من قبول سياسات RLS وStorage في بيئة Supabase الفعلية.

## حدود النسخة الحالية

- لا ربط مباشر بالأوتوكلاف، ولا تشغيل أو تحكم بالجهاز.
- التنبيهات تظهر من البيانات المسجلة عند تحميل/تحديث الصفحة؛ لا توجد مهام خلفية أو رسائل SMS أو بريد أو إشعارات دفع أو صوت.
- لا يوجد جدول آلي معتمد لدورية BI أو فحوص الأجهزة، ولا حساب مواعيدها تلقائياً. تُوثّق من السياسة المعتمدة وتتابع يدوياً في هذه النسخة. لا يعد التطبيق بديلاً عن برنامج المراقبة الروتيني.
- تبويب الأطقم مستخرج من الحمولات المسجلة؛ ليس مخزوناً مستقلاً ولا توثيقاً كاملاً لكل خطوات التنظيف والتغليف أو استدعاء الحمولات.
- لا يوجد دليل إجراءات سريرية مرفق تلقائياً، ولا توقيع رقمي قانوني، ولا توثيق مرضى.
- اعتماد الاستخدام يراجع نتائج الدورة والمعايير وBI إذا اشترط البرنامج أو كانت الحمولة تحتوي غرسة تبقى داخل المريض. صلاحية البرمجيات لا تعني اعتمادها السريري أو التنظيمي قبل مراجعة المنشأة.

## English summary

Two isolated branches, personal Supabase accounts, automatic operator/reviewer identity snapshots, four initially unassigned devices, device-specific approved programs, multi-item cycle entry, private attachments, audited revision and review workflow, in-app record-derived alerts, printable bilingual logs and CSV. The server uses the caller's verified JWT; ordinary actions do not use a service key. All application writes are permission-checked database RPCs, with read RLS and private Storage policies. Deploy on Render using the included blueprint. Actual Supabase/Render integration, staff provisioning and device program configuration remain required before operational use.
